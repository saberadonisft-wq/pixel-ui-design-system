# Raster pixel asset proof of concept

## Purpose

This proof of concept validates an asset-first pipeline: a generated RGB asset board is measured, cropped, conservatively keyed to binary transparency, and integrated into reusable responsive React components. Raster artwork supplies the visible frame, hardware, icon, and texture details. Live HTML supplies Vietnamese labels, amounts, descriptions, status, and interaction semantics.

Demo route: `/pixel-asset-demo` in the `@pixel-ui/example-asset-demo` workspace.

## Render contract

- Family: Ornamental Pixel Game UI
- Category: responsive pixel web UI backed by a game-interface asset system
- Grid: 4 CSS pixels
- Sprite scale: 1× natural size in product UI; contact sheets use a diagnostic 2× nearest-neighbor preview
- Frame method: CSS `border-image` nine-slice with 16-pixel top, right, bottom, and left slices
- Edge behavior: corners remain fixed; horizontal and vertical edge regions stretch only on their valid axis; center fill expands behind live content
- Light direction: top-left highlight and bottom-right shadow from the source raster
- Text: Cascadia Mono/Segoe UI fallbacks; Vietnamese strings remain selectable DOM text

## Source and manifest

- Source: `public/assets/pixel-ui/source/pixel-ui-sheet.png`
- Inspection: `public/assets/pixel-ui/inspection-report.md`
- Crop manifest: `public/assets/pixel-ui/asset-manifest.json`

Every manifest asset records a stable ID, type, measured crop rectangle, trim/background-removal behavior, output path, intended role, semantic theme, scaling behavior, and validation floors. Nine-slice frames additionally declare the four slice values.

The script checks that required component types are present, IDs are unique, crops stay in bounds, crops are non-empty, outputs are not fully transparent, alpha remains binary, dark interior pixels stay above configured preservation floors, and output paths cannot overwrite the source or escape the asset directory.

## Extraction

Pillow was already available in the local Python environment, so no additional image-processing dependency was added.

```sh
npm run assets:pixel-ui
```

The background strategy samples crop corners and flood-fills only boundary-connected pixels within a configurable RGB color distance. It never removes all black pixels globally. Enclosed dark centers and outlines remain opaque, and no feathering or semi-transparent halo pixels are introduced.

Generated files:

- Transparent PNG assets: `public/assets/pixel-ui/generated/`
- Dimension, alpha, dark-pixel, crop, and hash report: `public/assets/pixel-ui/generated/generated-metadata.json`
- Local light/dark contact sheets: `public/assets/pixel-ui/debug/contact-sheet-*.png`
- Local responsive and zoom renders: `public/assets/pixel-ui/debug/renders/`

The `debug/` directory is generated by the extraction and capture scripts and is intentionally gitignored. It is review evidence, not a runtime dependency.

## Component API

The shared implementation lives in `packages/react/src/PixelAsset.tsx`; reusable appearance lives in `packages/react/src/asset-styles.css`; the self-contained palette, geometry, fallbacks, and source paths are opt-in tokens in `packages/themes/pixel-assets.css`.

- `PixelAssetFrame`: raster nine-slice frame; accepts `tone` and structural `family`.
- `PixelDepositButton`: semantic button using the blue raster frame and a raster plus glyph.
- `PixelNavigationItem`: semantic pressed button using a tone-specific frame, fixed raster icon, live label, and non-color selected marker.
- `PixelIcon`: metadata-backed raster icon with explicit intrinsic dimensions and 1×/2× integer scale.
- `PixelCompactFrame`: fixed natural-size security or logout raster inside a labelled semantic button.
- `PixelContentPanel`: labelled semantic section composed from `PixelAssetFrame`.

Every interactive component provides default, hover, focus-visible, active, selected where applicable, and disabled behavior. Pressed controls move by one 4-pixel grid unit. Disabled styling changes both treatment and text decoration. Missing border images retain a dark surface and restrained inner fallback border; failed fixed icon images do not remove the accessible button name.

## Integer scaling and responsive composition

Product renders keep sprites at natural 1× dimensions and use `image-rendering: pixelated` plus `crisp-edges`. Asset width, height, x, and y are audited for integer alignment. Control grids use fixed grid-derived tracks where flexible fractions would otherwise put an image on a subpixel.

- Desktop: one-row account bar, four navigation modules, two-column content/status layout.
- Tablet: two-row account bar, two-column navigation, stacked content/status.
- Mobile: stacked account modules, one-column navigation, single-column content rows.
- Zoom review: 200% is captured as half-width CSS reflow with a 2× device scale; the smallest case clamps to the supported 320 CSS pixel layout.

## Known limitations

- The source is RGB and contains subtle baked glow/noise. Conservative removal retains a small amount of useful colored fringe rather than risking black-outline loss.
- The generated board has inconsistent outer padding and no authoritative slice guides. The measured 16-pixel slices work for the selected empty frames but should be replaced by artist-authored guides in production.
- Button samples with baked text, tightly spaced loose edge strips, and the assembled example are deliberately rejected.
- Frame centers contain source texture that stretches with the center region. A production asset pack should provide a tileable center and axis-repeat edge strips.
- Several source icons are 42×42 or 42×43 after safe trimming rather than standardized sprite boxes.

## Replacing the temporary sheet

Provide a production pack with transparent source PNGs, one file or explicit nine regions per frame family, authoritative slice metadata, tileable center/edge rules, standardized 32/48/64-pixel icon boxes, separate state frames, consistent padding, and no baked dynamic text. Update manifest coordinates/output names and semantic asset tokens, rerun extraction and contact-sheet review, then rerun `npm run test:asset-demo`.
